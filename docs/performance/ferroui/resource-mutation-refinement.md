# Resource-cache invalidation allocation refinement

The 24-scenario comparison at `77017ec27dd6c3105d3c23318a4125103a89bfd7` found that repeated deep resource mutation/lookup cost 48 rather than 24 managed bytes per operation and regressed 18.3% in the Linux non-tiered job. Read-only deep hits/misses improved 95.8%/98.2%, but those do not erase mutation costs. The mutation case was the only consistently out-of-envelope result in that job's calibration-informed screen. Evidence: [run 37904220720, job 113733890516](https://github.com/wieslawsoltes/Avalonia/actions/runs/37904220720/job/113733890516).

The cache previously cleared all locations on an epoch change, then allocated another weak handle for the same supplying dictionary. Each entry now has its own generation stamp and reuses its existing weak handle when revalidated. An entry from an old generation still misses; revalidating one theme/key does not validate any other entry. A missing location is explicitly distinguished from a collected location, and the weak handle can be reused when a previously missing key reappears. Obsolete lookup results cannot be published if their generation changed during traversal. Capacity remains bounded, and only weak references connect entries to removed resource graphs.

`FerroUiResourceMutationAllocationTests` verifies zero managed allocation across 1,000 warm-key invalidation/revalidation cycles, independence of per-entry/theme generations, missing-to-present transitions, and rejection of stale publication. Existing resource precedence, factory, reentrancy, weak-lifetime and browser pixel tests still apply. This eliminates the identified per-update handle allocation without weakening invalidation; timing and full mutation-path allocation must be read from the subsequent revision's run.
